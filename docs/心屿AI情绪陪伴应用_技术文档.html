01 / 项目与需求
PROJECT OVERVIEW

从“记录情绪”到“获得陪伴”

心屿面向学习、比赛和工作压力较大的年轻人。它不是冷冰冰的情绪打分工具， 而是一个能接住情绪、给出建议，并把变化可视化的桌面式陪伴应用。

用户痛点

情绪说不清

只写一句“烦”，很难判断压力来自哪里，也不知道下一步能做什么。

体验缺口

反馈太单一

常见工具只给分数或一句安慰，缺少既理解感受又提供行动建议的对话。

项目目标

一次输入，多角度回应

通过双 Agent 对话与情绪雷达，把“被倾听”和“知道怎么做”放在同一屏。

典型使用场景
01

赛后复盘：写下挫败感，感性与理性伙伴给出不同视角。

02

学习焦虑：识别焦虑、期待与平静状态，拆出可完成的小任务。

03

日常自省：用雷达图回看“今天的心情分布”。

架构设计原则
  • 分层清晰：页面不负责处理 Key 与上游 API。
  • 共享入口：前端只调用同域 /api/companion。
  • 数据可控：后端做强类型字段与角色顺序校验。

  • 可扩展：本地仍可用 Express 启动调试。
安全边界：浏览器代码中不包含 DeepSeek Key； Key 只写入 Netlify Production 环境变量并由 Function 读取。

03 / AI 技术方案
AI TECHNOLOGY · PRINCIPLES

一个模型，两种陪伴角色

我们没有为了“双 Agent”而调用两次 API，而是通过一个结构化 Prompt 让同一个语言模型同时扮演感性与理性角色。这样更省钱、更快，也更容易保持上下文一致。

感 feel · 感性伙伴

先复述用户的感受，不急着说教；语气温柔，允许情绪存在。 可以挑战理性伙伴过于冷静的表达，但不会否认用户的痛苦。

理 logic · 理性伙伴

尊重情绪，再把问题拆成低负担行动。建议具体、短小、可执行， 例如把任务拆成 15 分钟的小步骤，而不是只给空泛鼓励。

为什么选择 DeepSeek
选型维度 选择理由
中文表达 对中文情绪描述和日常语境理解自然，适合“陪用户聊天”的产品语气。
开发成本 接口与 OpenAI 风格兼容，前端/Node 集成简单；比赛周期内能快速跑通。
结构化输出 支持 JSON Object 模式，适合同时返回固定五项情绪分与对话数组。
响应速度 单次短文测试可快速返回；配合单次请求生成全部结果，交互等待可控。
可替换性 Prompt 与业务处理集中在后端服务层，未来可替换其他兼容模型。
为什么不用多模型

比赛产品的重点是把体验闭环做顺，而不是堆模型。一个模型承担两个角色， 可以降低调用费用、减少两次请求的不一致，也方便在一次返回中协调对话交锋。

为什么必须后端代理

API Key 一旦写进浏览器代码，任何访问者都能看到。后端代理把 Key 藏在服务端，同时统一处理超时、错误、用户输入长度与模型 JSON 异常。

03 / AI 技术方案
INTEGRATION & OPTIMIZATION

把自然语言变成可用的数据

用户只写一段日记，系统通过严格 Prompt 要求模型返回固定 JSON， 再由后端校验和清洗，最后交给前端直接更新图表与聊天列表。

1
输入日记用户描述真实感受与事件
2
发送请求POST /api/companion
3
服务端鉴权从环境变量读取 Key
4
模型生成严格 JSON Object 输出
5
校验清洗字段、数值、角色顺序
6
界面更新雷达图 + 多个气泡
核心 JSON 约定
{ "emotions": { "焦虑": 80, "喜悦": 20, "孤独": 60, "期待": 40, "平静": 50 }, "dialogue": [ { "role": "feel", ... }, { "role": "logic", ... } ] }
Prompt 关键约束：只输出 JSON；字段只能是 emotions 与 dialogue；分数必须是 0–100 的整数；两个角色交替，每人 2–3 条； 不诊断疾病，紧急情况优先关注现实安全。
集成方式
A

请求层：前端 fetch 同域 API，不接触任何密钥。

B

模型层：使用 deepseek-chat 与 JSON Object 模式。

C

校验层：后端解析 JSON，限制长度，清洗分数。

D

展示层：前端只处理通过校验的结构化结果。

优化策略

一次请求完成两件事

情绪分数与双 Agent 对话同时返回，减少等待与 Token 开销。

输出先收紧再兜底

Prompt 强约束 + response_format + 后端类型校验，三层降低格式失败。

异常可见但不崩溃

Loading、超时、鉴权、限流和 JSON 错误均在前端给出可读提示。

部署与运维要点

1. 同域转发

netlify.toml 把 /api/* 映射到 Functions，避免跨域与多地址管理。

2. 密钥隔离

.env 本地文件被 Git 忽略；线上 Key 存在 Netlify Secret 环境变量。

3. 费用保护

限制日记长度、单次调用 Token 和每分钟请求次数，降低误用风险。

部署经验：若面向国内评委，优先使用当前网络可正常解析的域名， 并把“页面可打开、API 可调用、真实模型可返回”作为三项独立验收条件， 不能只看平台显示“构建成功”。

06 / 总结与展望
INNOVATION & OUTLOOK

创新不只在“用了 AI”

真正有价值的创新，是把大模型能力变成用户能感受到的陪伴、能理解的图形和能继续执行的动作。

技技术创新点

  1. 单模型双角色编排：一个 Prompt 同时控制感性与理性 Agent，保证互动交锋并降低调用成本。
  2. 结构化结果闭环：JSON 模式 + 后端字段校验 + 前端防御性处理，让模型输出可直接驱动 UI。
  3. 情绪与对话同步生成：一次请求同时获得五维分数和对话数组，避免多次请求的等待与数据不一致。
  4. 前后端安全分层：Key 仅驻留服务端，公网入口统一为 /api/companion。

用应用创新点

  1. “被理解 + 有办法”的组合体验：感性伙伴接住情绪，理性伙伴给出实际下一步。
  2. 对话式情绪可视化：雷达图不是孤立仪表盘，而是与角色对话共同解释当前状态。
  3. 桌面小组件式界面：毛玻璃、留白和渐变让情绪工具更轻盈，降低使用心理门槛。
  4. 低门槛公网演示：一个链接完成输入、分析、对话和图表体验，便于比赛现场展示。
当前边界

不是医疗产品

情绪分数来自文本语义推断，仅用于自我觉察，不能替代专业评估。

上下文仍然较短

目前每次围绕一篇日记生成回复，尚未形成长期记忆与跨天趋势。

成本需要控制

公网演示已做基础限流，正式产品还需要账号、配额和持久化审计。

双 Agent 互动仍有限

目前以固定轮次生成对话，角色主动性、连续追问和长期互动深度仍可加强。

暂不支持自定义

宠物形象、名称、性格比例与回复风格尚未开放自定义，后续可加入个性化设置。

近期：体验增强

流式输出、情绪变化时间轴、用户可选择“更温柔 / 更理性”的回复比例。

中期：个性化陪伴

在用户授权下保留偏好与历史趋势，让宠物逐渐理解长期压力来源。

长期：多模态陪伴

加入语音语气、表情和桌面悬浮形态，形成更自然的情绪反馈入口。

让 AI 不只回答问题，也能先接住情绪。

心屿希望把大模型从“聊天窗口”变成真正有分工、有温度、有行动建议的桌面伙伴。 对比赛而言，它已经形成了一个可展示、可验证、可继续扩展的完整原型。
